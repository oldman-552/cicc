# Manually scoped asset inventory

This is a development feature for manually recording asset metadata. It **does not discover, resolve, connect to, scan, exploit or assess** an asset. Identifiers are treated as text, not independently validated evidence of ownership, authorization, reachability or exposure. An authorization attestation and a free-text scope basis are required on creation; these are user claims, not verified permission. Never use the demo preview for sensitive asset information.

Analysts/admins can register an asset, retire it or reactivate it with a fresh authorization attestation. Viewers have read-only access. Asset records use experimental application-level workspace scoping, with no production tenant or per-asset isolation. Asset identifiers and scope basis may be sensitive; they are not encrypted or access-controlled beyond the development roles. Active asset metadata can be edited with a fresh attestation. After an investigation or SBOM link exists, its type and identifier cannot be changed; register a new asset instead. Existing snapshots and associations are not independently reverified by edits. There is currently no deletion, import, expiry, approval workflow or independent ownership verification.

An active asset can be linked to an investigation. The link preserves a metadata snapshot and records the actor/time, marked `USER-ATTESTED` and `UNVERIFIED`. Later retirement does not alter the historic snapshot. The investigation report and graph show explicit links only; a link does not establish that a vulnerability affects an asset or that it is exposed. The investigation selector shows at most the latest 100 active assets.

An active asset can also be associated with an imported SBOM after a separate user attestation. The association preserves SBOM summary and candidate count at link time. It does not establish that the inventory was deployed on that asset; candidates are not confirmed vulnerabilities. The selector shows the latest 100 SBOMs, and the association list returns up to 100 links. SBOM comparison limitations still apply; see [SBOM.md](SBOM.md).

API routes: `GET/POST /api/assets`, `GET/PATCH /api/assets/{id}`, `PUT /api/assets/{id}/metadata`, `POST /api/investigations/{id}/assets`, and `GET/POST /api/assets/{id}/sboms`. Writes require CSRF protection and analyst/admin role outside demo mode. Status changes and links create local audit entries, which are not tamper-resistant.


PostgreSQL asset metadata/status mutations and both supported link operations now lock the asset row before checking or changing it. This is intended to serialize concurrent API link creation with identity changes or retirement; selected race tests are pending PostgreSQL CI. SQLite does not provide PostgreSQL-style row locks; concurrent behavior there is not certified. These locks do not establish tenant isolation or protect against privileged direct database writes.
