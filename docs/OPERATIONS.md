# Development operations and limitations

- Start locally using the README. Alembic migrations are required before the API starts accessing tables. `DATABASE_URL` defaults to `sqlite:///./cicc.db`; PostgreSQL requires a psycopg SQLAlchemy URL.
- Create workspaces with `python -m backend.app.workspaces SLUG NAME` and accounts with `python -m backend.app.accounts USER --role admin|analyst|viewer --workspace SLUG` (defaults to `default`); the command prompts interactively and does not accept the password as an argument. No default accounts are created. Changing or disabling an account invalidates existing sessions. Use `python -m backend.app.accounts USER --workspace SLUG --disable` to disable without a password prompt; configuring the account again with a new password re-enables it. Local CLI changes write mutable audit entries as the unverified actor `local-cli`.
- Source refresh is manual. FIRST EPSS requires approved egress to api.first.org and cached GitHub advisories; the live FIRST API has not been tested here. GitHub API limits and network failures are possible; a failed refresh retains previous cached data and exposes source health. CISA, CVE Program and ATT&CK Git blob hashes are checked for integrity; these are not independent signatures or verification. ATT&CK refresh selects a deterministic sample of ten STIX files, not the entire catalog. CVE Program refresh requires previously cached GitHub advisories and fetches at most 10 referenced records; failure leaves the prior cache intact.
- The Compose files are a proposed development setup only. Docker was unavailable and their runtime behavior was not verified. No production deployment guide is claimed.
- No encrypted backup or tested restore mechanism is provided. For development SQLite, stop writes and use SQLite's online backup API; for PostgreSQL use controlled database-native backup procedures. These are operational suggestions, not verified recovery instructions. No RPO or RTO has been validated.
- Do not expose the development server or demo mode publicly. No TLS termination, secret manager, enforced enterprise MFA, production tenant isolation, secure evidence vault or production audit control is included. Local TOTP needs a stable external key; offline global key rotation requires verified downtime and both keys; see [MFA.md](MFA.md).

## Disposable PostgreSQL integration test

A CI job defines a temporary PostgreSQL service, applies migrations and runs `backend/tests/test_postgres_integration.py`. Selected revisions through scoped-link race test commit a2ad650 passed GitHub Actions against a disposable PostgreSQL service; these checks were not run locally. Later changes require their own CI run. The tests **commit writes**; one also attempts a guarded downgrade. They are skipped unless `CICC_TEST_DISPOSABLE_DB=1`, `DATABASE_URL` and `CICC_TEST_POSTGRES_URL` are the same PostgreSQL URL. Use only a disposable, pre-migrated database; never use shared or production data. Passing these tests would not establish tenant isolation, production security or recovery readiness.

- Public source caches and refreshes are global across workspaces; failed/unknown login audits are unscoped and not visible via workspace audit. Workspace scoping is not a production security boundary. See [WORKSPACES.md](WORKSPACES.md).

## Development health checks

`GET /api/health` is liveness only and does not query the database. `GET /api/ready` checks basic database access and two identity-schema columns. Outside demo mode it also validates the MFA key if policy is enforced or an account is enrolled, and attempts to decrypt one enrolled seed when present. It returns only `ready` or `not_ready`, without database/secret details. A successful result does **not** verify every migration, trigger, account, source, authorization policy, production dependency or disaster-recovery capability. It checks one MFA record only. The proposed Compose health check uses this readiness endpoint, but Docker/Compose execution has not been verified here.

- The [SQLite development copy utility](RECOVERY.md) does not cover PostgreSQL, encryption, authentication or production recovery. Restoring an old snapshot can revive revoked sessions and security settings.

- Login throttling uses database transaction locks: PostgreSQL advisory locks serialize account and observed-client checks across updated workers sharing one database; SQLite uses a coarse write lock and may return 503 under contention. All workers must be upgraded; mixed versions bypass the serialization. Counts are time-windowed using application clocks. The observed peer address depends on trusted proxy configuration; do not trust arbitrary forwarded headers. This is not a substitute for edge defenses, robust distributed throttling, lockout recovery, monitoring, or DDoS protection. PostgreSQL concurrency tests await CI.
