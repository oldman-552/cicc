# Development workspace scoping

This is an application-level development feature, **not production tenant isolation**. It must only be used with non-sensitive test data in a trusted environment. Requests using local accounts scope investigations, their evidence/notes/events/links, manually entered assets, SBOMs and authenticated audit events to the account's active workspace. Roles are shared across each workspace, not per-object permissions. The interface displays the workspace name. Demo mode bypasses authentication and always uses workspace `default` (ID 1).

Public advisories, CISA KEV, CVE records, ATT&CK techniques and source status are global: every workspace sees the same cache, and an admin in **any** workspace can refresh it for everyone. Global source changes are not independently isolated. Login failures for an unknown, inactive or unavailable account are unscoped and the workspace audit endpoint does not expose them; failures for a known active account are attributed to that account’s workspace. Admins cannot use it to investigate all authentication failures. Audit is mutable and not suitable for compliance or forensics.

## Local administration

With the virtual environment active and migrations applied:

```sh
python -m backend.app.workspaces research 'Research development'
python -m backend.app.accounts alice --role admin --workspace research
python -m backend.app.accounts bob --role analyst --workspace research
# Disable an account and revoke all sessions; no password prompt.
python -m backend.app.accounts bob --workspace research --disable
python -m backend.app.workspaces research --disable
python -m backend.app.workspaces research --enable
```

Workspace creation and account management require trusted local server/database access. Passwords are prompted interactively, never passed on the command line. Omitting `--workspace` chooses `default`. Workspace slugs are lowercase letters, digits and single internal hyphens, 1–40 characters. Existing accounts cannot be moved with this CLI; updating or disabling an account revokes its sessions. Re-enable by configuring the account with a new password. CLI workspace creation and account configuration/disable write audit entries transactionally as `local-cli`; this is an unverified label, not attribution to an individual operator, and does not protect against direct database changes. The trusted CLI disable/enable operations each revoke all workspace sessions and add a mutable `local-cli` audit entry in the same transaction. Already-started requests may finish. PostgreSQL login and account configuration serialize with these operations through workspace row locks; this serializes concurrent logins within a workspace and has not been load-tested. SQLite has no equivalent row locking, so concurrent lifecycle/login safety is not certified. Manually editing workspace state directly in the database bypasses this workflow: deactivation alone blocks sessions only while inactive, so unexpired sessions may revive on reactivation. No independently attributed administrative approval flow exists. There is no management UI, self-service enrollment, account migration or audited administrative approval flow.

Migration `b8936d1c2327` places existing records, including legacy audit entries, in `default`, because their historical workspace is unknown. This is a migration convention, not evidence of their origin. The downgrade is refused if additional workspaces or scoped records remain. Back up data and review migrations before use; only synthetic SQLite copy-to-new recovery has been tested, not production recovery.

## Security limits

The service checks workspace ownership in the implemented endpoints and checks both ends of manual links. An ORM hook requires explicit workspace IDs for protected root objects and rejects reassignment. Migration `484b2e0f87f1` adds SQLite triggers or PostgreSQL foreign keys and triggers that validate root workspace references, prohibit root reassignment, and reject cross-workspace investigation–asset and asset–SBOM links even through ordinary direct SQL. Existing inconsistent rows cause the migration to abort before creating guards; repair must be deliberately reviewed. Stop all writers during migrations: preflight and guard installation do not constitute a concurrency-safe online rollout. SQLite schema comparison intentionally excludes workspace foreign-key metadata because the deployed SQLite migration uses triggers rather than actual FKs; `alembic check` does not validate triggers. The ORM and triggers do not cover every invariant or privileged database operations. Server defaults can still supply workspace 1 to direct SQL. A sufficiently privileged database user can alter or disable protections. There is no row-level security, composite workspace foreign-key enforcement across all related records, hardened administrative boundary, comprehensive concurrency testing or independent penetration test. The guard migration has been exercised with direct SQL on SQLite and on disposable PostgreSQL in GitHub Actions; these limited tests do not establish concurrency safety or production isolation. Isolation in a real deployment has not been verified. Do not market these checks as enterprise isolation. A database administrator or application bug can bypass them.

SQLite DDL can be non-transactional: a failure or interruption during schema changes may leave partial triggers. Use a tested backup, inspect schema and Alembic revision, and perform a reviewed recovery rather than assuming rollback. The migration downgrade uses `DROP TRIGGER IF EXISTS` to allow recovery from an interrupted guard removal. Downgrading removes these safeguards. No production recovery procedure or drill is claimed.


Migration `a63c9f170b42` adds parent-reference immutability for evidence, notes, investigation events/technique references, SBOM components and candidates. A preflight rejects existing orphaned rows without changing them; it cannot detect historical reassignment or establish original ownership. Downgrade refuses while any of those child records exist, because removing these guards weakens protection. Stop writers before migrating and take a separately verified backup. SQLite migration and direct-SQL tests passed locally; PostgreSQL guard and link/delete race tests passed in disposable GitHub CI for commit 9a2c12d. These triggers do not provide RLS, stop delete/re-insert, prevent privileged schema changes or protect record contents from modification.


Only `admin`, `analyst`, and `viewer` are accepted by login and session validation; an unexpected database role fails closed. Repair roles through the trusted account CLI, which revokes sessions. Direct SQL changes to a valid role bypass this revocation workflow, and sessions blocked only by an invalid role can become usable again if changed back outside the CLI. This is not per-object authorization or a substitute for database isolation. PostgreSQL verification of runtime rejection passed in disposable CI for commit cfb48c4.


Migration `c1af7842d90b` additionally rejects invalid account roles via SQLite triggers or a PostgreSQL check constraint. Existing unsupported values fail preflight without automatic repair. Downgrade is refused while accounts exist, because it removes this guard. Stop writers during migrations and review any invalid legacy roles with an authorized operator. The SQLite guard has been tested locally; PostgreSQL migration validation is pending CI. This constrains allowed strings only; it does not prevent privileged database users from assigning another valid role or bypassing schema protections.
